# 网络与响应监测

主卡的“网络与响应”显示当前判断和 Codex 轻量探测耗时，点击查看详情、立即探测或暂停。正在工作时每 15 秒采样，空闲时每 60 秒；每个目标最多等待 8 秒，探测在后台运行，不阻塞浮窗，也不发送模型请求。

## 两组证据

- 主动探测：无凭据 GET `https://chatgpt.com/backend-api/codex/models`（401 为预期）与 `https://www.gstatic.com/generate_204`（204 为预期）。保存状态码、耗时和失败类型，不保存响应正文或凭据。
- 当前聊天：只读本地日志中的请求开始、响应头和模型输出事件元数据。显示距上次事件时间、近 5 分钟连接异常，以及界面设置与最近请求的思考强度。不会读取或展示推理正文。

通过现有 Mihomo 命名管道只读查询 TUN 状态和 ChatGPT 连接路径。TUN 开启时按系统网络发送；否则有可用 mixed-port 时使用本机代理入口，并明确显示该方式。无法读取时标记路径未验证，不能声称已探测当前节点。对照域名可能命中不同分流规则。

## 判断边界

- 连续两次超时或明显变慢：两目标同时出现则标网络路径可疑，仅 Codex 出现则标 OpenAI 路径可疑。
- 变慢阈值：大于 2.5 秒且大于之前样本中位数的四倍；基线不含正在比较的两次样本。这是诊断线索，不是 SLA。
- 单次失败/抖动先标波动，不直接归因。HTTP 403、429、5xx 与连接失败分开；curl 不可用时显示未验证。
- 当前聊天持续出现模型事件：只说明还在收到数据，不证明模型速度正常，也不排除网络抖动。
- 探测可达但聊天无事件：原因待确认，不能区分服务端排队、计算或长连接停顿。
- 工具执行、等待输入、已完成等状态不会当作模型断流。
- 事件间隔不是逐 token 心跳；请求至响应头包含上传、网络和服务端等待。
- 缺失、过期数据不沿用正常判断。切换 ChatGPT 路径后清空探测基线；样本只在内存中保留最近 5 分钟，最多 24 次。

所有操作只读；不会切节点、清连接、修改 Codex 参数或重启任务。只提示可能原因，确认某个节点的影响仍需要控制其他条件的对照实验。
